### 第二轮交叉攻击与唯一裁决（本轮变化）

**争议点 G：同进程可重放 SSE 是否可以关闭“可靠重连”问题**

- FDE 反驳可靠性：即使事件不丢，用户在进程重启后仍无法验证工具副作用或取得最终结果；“三次重试”不是可恢复交付。
- 可靠性反驳 FDE：不能为了无限等待而让 UI 假装已完成；`unconfirmed + requestId + Stop` 是当前可验证的 fail-closed 行为，但不是 durable completion。
- 测试破坏官攻击建设者组：旧 Queue 的消费竞争已被 journal 测试覆盖，但 journal 的内存上限可被高频事件触发；必须显式 error，且本轮已验证，不得 silently truncate。
- 运维反驳测试破坏官：测试的 `SimpleNamespace`/本地 WSGI 不覆盖真实反向代理、worker 回收和多实例；部署 VETO 维持。
- 治理结论：不得以恢复便利引入长效 bearer query；cursor 必须继续在 one-shot ticket 内，而非 URL 自证或客户端可签发。
- **唯一推荐方案**：保留当前 owner/request/cursor-bound ticket + bounded journal + `unconfirmed` UI；下一阶段新增持久化 run/event journal、可认证的结果查询、重启/多实例恢复和真实网络/代理故障演练。禁止把本轮 local PASS 写为生产 SSE 闭环。

### 2. 执行可靠性架构师

#### P1-REL-01：SSE ticket 为进程内状态，重启/故障转移不可恢复

**引用**：`channel/web/web_channel.py:285-286,524-561`。  
**问题**：票据、request owner、SSE 队列均为内存结构，进程重启会丢失票据和流状态。  
**建议**：将可恢复任务落到持久 outbox/任务表；重连使用持久 request 状态和历史恢复。

#### P1-REL-02：一次性 ticket 的防重放与可靠重连存在张力

**引用**：`channel/web/web_channel.py:524-561,2875-2900`；`client.ts:148-159`。  
**问题**：一次性消费可被窃取者先消费造成 DoS；改为可重复又引入 replay 窗口。  
**建议**：保持一次性、request/owner 绑定、60 秒 TTL；合法客户端用 header auth 重新申请并恢复，重连次数和截止时间有界。

#### P1-REL-03：数据库损坏路径会 quarantine 后创建空数据库

**引用**：`agent/memory/storage.py:180-217`。  
**问题**：损坏后继续启动空库可能被误认为“数据为空”，导致历史不可见并写入错误状态。  
**建议**：默认阻断启动；只有显式恢复命令才能创建新库，并在 UI/readiness 显示恢复阻断。

#### P1-REL-04：迁移/回滚没有真实演练证据

**引用**：manifest 的 `MIGRATION_ROLLBACK_TEST=NOT_RUN`；`tests/test_operational_readiness.py:38-55`。  
**问题**：单元迁移测试不覆盖旧版读取新 schema、回滚后写入、崩溃窗口和备份恢复。  
**建议**：建立旧版→新版→故障→回滚矩阵，保留数据库 hash、迁移日志和恢复结果。

#### P2-REL-05：readiness 尚未覆盖外部依赖与长期队列行为

#### P1-OPS-01：发布证据未绑定受保护构建、签名、Docker、安装器与长期运行证据

**引用**：`benchmarks/results/release-evidence-manifest.json` 的本地 `GIT_COMMIT_BOUND_EVIDENCE=YES`（仅 clean local commit）、`SIGNED_RELEASE_ARTIFACT=ABSENT`、`DOCKER_BUILD=NOT_RUN`、`INSTALLER_SMOKE_TEST=NOT_RUN`、`72H_SOAK=NOT_RUN`、`PRODUCTION_ALERT_FIRE_TEST=NOT_RUN`。

**问题**：本地报告不能证明 CI 构建出的二进制就是客户实际部署的二进制，也不能证明升级、告警和 72 小时运行行为。

**建议**：使用受保护 CI 生成带 commit/tree hash、SBOM、签名和 provenance 的制品；在客户等价环境执行安装、升级、回滚、soak 和告警 fire test，并保存不可变证据包。

#### P1-OPS-02：镜像发布 job 缺少测试依赖、使用 mutable tag

**引用**：`.github/workflows/deploy-image.yml`、`.github/workflows/deploy-image-arm.yml` 的构建与推送步骤。

**问题**：构建/推送路径未强制依赖完整测试和可信 manifest，`latest` 等可变 tag 使回滚和二进制对应关系不确定。

**建议**：镜像 promotion 必须 `needs` 受保护 preflight；只推送不可变 digest/tag，生产部署记录 digest，不接受 `latest` 作为发布身份。

#### P1-OPS-03：依赖、基础镜像、安装器工具没有全部锁定

**引用**：`requirements.txt`、`desktop/build/requirements-desktop.txt`、`docker/*`、`.github/workflows/release-win7.yml`。

**问题**：未固定的 pip/npm/action/apt/基础镜像或运行时下载会导致同一源码产生不同制品，并引入供应链漂移。

**建议**：提交 lock/hash、固定基础镜像 digest 和 action SHA；所有下载物做 SHA-256/签名校验；禁止发布 job 使用 `latest` 或无校验远程 CLI。

#### P1-OPS-04：代码签名/公证是可选路径

**引用**：`desktop/electron-builder.win.js:50-56,101-105`、`desktop/build/notarize-dmg.sh`、`.github/workflows/release.yml`。

**问题**：缺少签名配置时构建仍可继续，未签名安装器可能进入发布链路。

**建议**：生产 profile 缺少签名密钥、证书主体或公证结果必须硬失败；unsigned 仅允许隔离 dry-run，不能写生产 R2/D1。

#### P1-OPS-05：没有可验证的 promotion/rollback 原子边界

**引用**：`.github/workflows/release.yml`、`release-win7.yml`、`release-overlay.yml`。

**问题**：人工 dispatch、制品上传、feed 更新、D1 注册和 latest promotion 之间缺少事务性及反向回滚演练；失败时可能出现 R2 有包而 feed 指向旧包的混合状态。

**建议**：采用候选版本→完整校验→原子 promotion；保留上一版本指针，演练失败回滚并验证旧客户端读取新数据/旧 feed。

#### P1-OPS-06：数据库损坏时 quarantine 后创建空库，更新脚本缺少 rollback

**引用**：`agent/memory/storage.py:180-217`；部署/更新脚本中直接 pull/restart 路径。

**问题**：损坏文件会被移走后启动空数据库，用户可能把数据丢失误判为“没有历史”；升级失败也没有可验证恢复点。

**建议**：默认 fail-closed；只有显式恢复命令创建新库；备份、迁移、回滚必须带 hash、版本和恢复结果。

#### P1-OPS-07：密钥日志与文件权限边界不足

**引用**：`common/config.py:432-440`、`.env` 写入与备份路径。

**问题**：配置/备份可能记录或保存 API key，写入未统一保证 `0600`/Windows ACL；日志和备份泄露会绕过应用鉴权。

**建议**：统一 secret redaction；密钥文件创建即设置最小权限；备份默认排除 secret，恢复前做权限/owner 检查。

#### P1-OPS-08：Docker 网络和隔离默认不满足生产收敛条件

**引用**：`docker-compose*.yml` 的 `WEB_HOST=127.0.0.1` 与端口发布、`seccomp: unconfined`、可变镜像 tag。

**问题**：绑定/端口语义容易被误解，`unconfined` 扩大容器逃逸面，且缺少健康检查、资源上限和自动恢复。

**建议**：明确 TLS reverse proxy→loopback 方案；移除 unconfined；固定 digest；加入 healthcheck、restart policy、CPU/内存/磁盘上限和告警。

#### P1-OPS-09：安装/更新远程脚本与内容校验可能 fail-open

**引用**：安装器更新、feed 和远程脚本路径；`release-overlay.yml`。

**问题**：远程地址、重定向或包内容未绑定公钥/hash 时，网络被劫持或仓库被替换即可执行非预期代码。

**建议**：只允许受信域名和 HTTPS；固定 digest/signature；下载后先离线验证再安装，失败必须阻断，不得回退到未校验内容。

#### P1-OPS-10：feed key、平台架构和并发上传存在覆盖风险

**引用**：`release-overlay.yml:270-290`、制品 flatten 步骤。

**问题**：macOS arm64/x64 写同一 feed key，或相同 basename 互相覆盖，导致客户端拿到错误架构/旧 hash。

**建议**：按 OS/arch 分离 feed 或原子合并 metadata；flatten 前检查 basename 冲突；发布前验证每个平台制品、hash 和 feed 映射完整。

#### P1-OPS-11：发布 job 权限和输入注入面过大

**引用**：`.github/workflows/release.yml:31-33,98-108,195-213`、`.github/scripts/register-releases.mjs:36-49,93-121`。

**问题**：`workflow_dispatch` 的 version/overlay ref 未统一 SemVer/allowlist 校验，shell/SQL 拼接和 `contents: write` 会把被注入输入直接带入具备秘密的 runner。

**建议**：输入先通过独立 allowlist job，再通过 `env` 传递；使用参数化 SQL/Node crypto；build job 只读，promotion 单独最小权限且需要审批。

#### P1-OPS-12：监控只验证本地 readiness，没有生产告警闭环

**引用**：`channel/web/web_channel.py:2366-2414`、manifest 的 `PRODUCTION_ALERT_FIRE_TEST=NOT_RUN`。

**问题**：readiness 通过不等于模型、队列、R2/D1、外部渠道和长时间连接正常；没有生产故障触发到通知人的证据。

**建议**：区分 liveness/readiness/degraded；接入依赖探针、队列/内存/连接/错误率指标；在受控环境执行告警 fire test 并保存通知链路证据。

## 第二轮分组交叉攻击

### 争议点 A：Delivery 只读门禁是否足以形成交付闭环

- **FDE 立场**：当前桌面 Delivery 页已经避免 UI 自签 PASS，但客户仍不能在产品内完成 case、条目、签名和证据 hash 绑定。
- **治理/红队反驳**：即使增加本地“接受”按钮，同一工作树仍可修改状态机和 manifest；本地写入不能成为外部证明。
- **运维补充**：生产部署还缺少制品 digest、签名、客户环境标识和部署版本回读。
- **最终唯一推荐**：保留只读 Delivery 页；验收必须是服务端不可变审计记录，绑定 customer/case、manifest hash、commit/tree、制品 digest、执行环境、操作者和客户签名；签名包由受保护外部 runner 生成，产品只能展示/校验，不能创建 PASS。

### 争议点 B：SSE 一次性 ticket 与可靠重连

- **可靠性立场**：当前 ticket 在进程内，断线/重启丢失；一次性消费防 replay，但盗用者先消费可造成 DoS。
- **测试破坏反驳**：不能为了重连而允许 bearer query 重放；必须攻击“错误 request_id、重复消费、抢先消费、断线后重连、进程重启”五条路径。
- **FDE 结论**：断线不能显示最终完成；当前桌面仍缺少 ticket 重发和历史恢复。
- **最终唯一推荐**：保留 owner/request 绑定的一次性 ticket；增加认证 header 的有限重连接口、服务端 durable run 状态/历史恢复和 `incomplete/unconfirmed` UI；重连次数、TTL、退避和截止时间写入合同，严禁恢复为长期 bearer query。

### 争议点 C：文件服务安全边界与产品可用性

- **FDE 立场**：图片、音频、下载和预览必须可用，不能只在 API 中安全而在 UI 中不可见。
- **治理/红队反驳**：`withToken` 仍把 bearer 放入非 SSE 文件 URL，历史、代理和日志可能泄露；直接开放 filesystem root 是不可接受的便利路径。
- **最终唯一推荐**：workspace 默认根、owner upload 根、preview/citation capability 三者分开；拒绝 filesystem root 和跨 owner path；文件 URL 改为短 TTL、路径/owner/用途绑定 capability 或 renderer authenticated fetch blob，逐步移除 bearer query。

### 争议点 D：仓库内 preflight 是否等于受保护 CI

- **治理立场**：同一 PR 可以修改 verifier、策略、workflow 和报告；preflight 只能证明当前代码自洽。
- **运维反驳**：即便 workflow 静态上有 `needs`，当前仓库未提供 protected branch、required check、签名 attestation 和真实 deployment evidence。
- **最终唯一推荐**：仓库内 preflight 只作为必要条件；最终 gate 必须由固定 SHA 的外部 verifier/受保护 runner 验证 commit/tree、manifest、报告 hash、制品签名和环境 attestation，且写权限仅授予 promotion job。

### 争议点 E：本地性能 PASS 是否能推断 SmartAssistant/客户环境性能

- **FDE/性能证据**：CMRC2018 全量 3219 queries 上，improved Recall@1 `0.1121→0.8984`、Recall@10 `0.1417→0.9487`、平均延迟 `2.2025→1.2086 ms`，当前 comparison `passed=true`。
- **运维反驳**：这是 Windows 本地单环境证据，不覆盖客户硬件、并发、模型供应商、磁盘、网络、72 小时资源曲线和部署制品。
- **最终唯一推荐**：保留当前回归作为模块性能下界；补充 SmartAssistant 同版本基线、客户等价负载、并发/尾延迟/内存/连接/磁盘/错误率和 72 小时 soak，所有结果绑定制品 digest 和环境快照，改进模块必须在同一协议下严格胜出。

### 争议点 F：修复范围是否可以只覆盖本轮新增攻击

- **破坏者立场**：现有会话、scheduler、background bash、Memory、evolution、文件写入仍存在旧并发/越权/假成功路径，不能因为 Web boundary 26 checks 通过就关闭。
- **可靠性反驳**：这些路径若没有 session lock、generation fencing、durable journal 和跨进程锁，正常回归并不能证明恢复。
- **最终唯一推荐**：以不变量为合同：未经授权零读取/零写入/零取消副作用；同一 request 重试零重复副作用；清理/删除后旧 generation 零提交；崩溃恢复不把损坏数据当空数据；所有错误状态不得返回 success。

## 第三轮联合最终否决

由于当前仍有硬否认项，五个启用角色均不能批准关闭。

### FDE 产品交付官：VETO

**阻断条件**：目标客户必须在签名制品上执行完整 case（登录、聊天/SSE、取消、上传、知识库引用、历史恢复、交付证据）并提交 customer/case、环境、时间、操作者、实际结果、签名和 manifest SHA；当前 `TARGET_CUSTOMER_ACCEPTANCE=NO`、`CUSTOMER_TEST_EXECUTION=NOT_RUN`，未满足前不得声明可交付。

### 执行可靠性架构师：VETO

**阻断条件**：必须有可复核的旧版→新版迁移/回滚、损坏数据库恢复、commit/rename/fsync/双恢复者故障注入、SSE 重连/重启和 72 小时资源/队列证据；当前 `MIGRATION_ROLLBACK_TEST=NOT_RUN`、`72H_SOAK=NOT_RUN`，未满足前不得关闭。

### 治理与红队审计官：VETO

**阻断条件**：源文件必须被受保护 Git commit/tree 完整跟踪；required checks、branch protection、外部 verifier、签名 attestation 必须在仓库外或受保护 runner 中真实执行；当前本地 `GIT_COMMIT_BOUND_EVIDENCE=YES` 但 `BRANCH_PROTECTION=ABSENT`、`EXTERNAL_VERIFIER_ATTESTATION=ABSENT`，未满足前所有本地 PASS 仅为本地结果。

### 测试破坏官：VETO

**阻断条件**：在客户等价制品上，使用生成式路径/owner/session/请求/文件输入组合，覆盖乱序、重试、并发、取消、超时、错误边界；对每个 COMMIT/rename/fsync/时钟边界注入故障，并由 invariant checker 证明零越权、零重复副作用、零旧 generation 提交；当前 `CUSTOMER_TEST_EXECUTION=NOT_RUN`，未满足前不得关闭。

### 运维与部署审计官：VETO

**阻断条件**：必须有可复现构建、固定依赖与基础镜像 digest、签名安装器/Docker 制品、安装/升级/回滚 smoke、密钥/权限审计、72 小时 soak 和生产告警 fire test；当前 `REPRODUCIBLE_BUILD=NOT_RUN`、`SIGNED_RELEASE_ARTIFACT=ABSENT`、`DOCKER_BUILD=NOT_RUN`、`INSTALLER_SMOKE_TEST=NOT_RUN`、`PRODUCTION_ALERT_FIRE_TEST=NOT_RUN`，未满足前不得发布。

### 明确拒绝的绕过方案

1. **拒绝**：用本地 `generate_report`/`verify_report` 或本地 `release_manifest` 的 `passed=true` 代替外部 verifier、Git 保护和客户证据。
2. **拒绝**：把 `N/A`、`pending`、`NOT_RUN`、`ABSENT` 改写为 PASS，或在 UI 中隐藏 denial。
3. **拒绝**：把本地测试、模拟部署、脚本输出或旧报告复制件当作客户/生产执行证据。
4. **拒绝**：为了可靠性恢复长期 bearer query、开放 filesystem root、取消 owner 校验、允许同一 PR 改门禁规则后自证。
5. **拒绝**：以性能基准局部超越推断全产品、客户环境和部署后均超越；必须补客户等价负载和制品绑定证据。
