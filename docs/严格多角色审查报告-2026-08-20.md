## 第二轮交叉攻击记录与唯一裁决

### 争议点 A：SSE 游标修复能否关闭"可靠重连"

- **FDE 攻击**：游标修复只保证事件流不重复、不丢失前缀；用户仍无法查询崩溃 worker 的业务结果，`unconfirmed` 不是可交付状态。
- **可靠性反驳**：同意；但本轮修复消除了"重连从 0 重启导致整段重放"的错误恢复路径，这是必要非充分条件。
- **测试破坏官补充**：已验证去重守卫拒绝 `id <= lastEventId` 的重放帧；但服务端全帧带 id 仅是代码走读结论，缺 boundary 断言。
- **唯一裁决**：标记 P1-FDE-03/P1-REL-02 为"部分修复"；boundary 报告补"全帧单调 id"检查（FDE-20）；worker 结果查询与人工处置仍为关闭前必须项。

### 争议点 B：Python 版本敏感门禁是否构成绕过路径

- **治理立场**：构成。版本错误 → 门禁误红 → "重新冻结哈希"即可消红，这与"手改报告为 PASS"同构。
- **运维反驳**：不是代码缺陷而是环境缺陷；但环境不可重建（OPS-13）放大了该风险，因为任何人无法验证"正确环境"是什么。
- **唯一裁决**：门禁内硬断言解释器版本（REL-24）；冻结基线哈希的操作必须记录冻结 commit、解释器版本与双人复核；验证环境锁定文件入库（OPS-13）。

### 争议点 C：本地 commit-bound 证据的效力边界

- **治理立场**：HEAD 28ec476 的 `GIT_COMMIT_BOUND_EVIDENCE=YES` 只证明"本地这个 commit 的树被完整跟踪"，同一作者可任意重写历史。
- **FDE/运维同意**，并指出：本轮正是靠 manifest 的 `STALE_SOURCE` 拒绝才避免了"以旧报告冒充新证据"——该机制应写入合同作为强制控制。
- **唯一裁决**：本地 commit-bound 作为发布的必要非充分条件保留；`BRANCH_PROTECTION`/`REMOTE_CI_REQUIRED_CHECKS`/`EXTERNAL_VERIFIER_ATTESTATION` 未满足前，任何"commit-bound"表述必须带"仅本地"限定词。

### 争议点 D：已修复项能否在无客户环境下标记"关闭"

- **测试破坏官立场**：不能。"已修复并复验"仅指本地回归；scheduler owner 隔离等修复的多进程/真实代理攻击未执行。
- **FDE 反驳**：若一律不许标记，审查失去渐进性；建议分级："本地复验关闭"与"生产关闭"两档。
- **唯一裁决**：采用两档标记。本轮所有"已修复并复验"均为**本地复验关闭**；生产关闭仍挂靠在 P0-CHAOS-01/P0-FDE-02 的客户执行证据上。
