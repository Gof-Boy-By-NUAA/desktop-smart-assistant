title: knowledge-wiki

---

Organises notes, insights, and reference materials from your conversations into a structured local knowledge base, automatically maintaining an index and cross-references between pages.

`knowledge-wiki` uses SmartAssistant's governed knowledge tools and SQLite fact store. The workspace `knowledge/` directory is a generated read-only view, not the writable source of truth. The skill is marked `always: true`, so it is **always loaded** and requires no external dependencies.

## When It Triggers

- You share an article, document, or URL that you want to keep for future reference
- A conversation produces conclusions worth retaining long-term
- You want to look up something you accumulated earlier

## Directory Structure

```
knowledge/
├── index.md           # Generated global index (read-only)
├── log.md             # Generated lifecycle log (read-only)
└── <category>/        # Category subdirectories (grouped by content)
    └── <slug>.md      # Knowledge page (lowercase-hyphenated filename)
```

## Three Core Operations

### 1. Ingest

When you share some material, the Agent will:

1. Read and understand the original content, extracting key information
2. Use `knowledge_search` to find related governed documents and avoid duplicates
3. Call `knowledge_write` with a stable `source_ref`, collection, scope, and sensitivity
4. Keep the returned document ID and immutable version when they are useful to the user

### 2. Synthesise

When a conversation produces new conclusions or insights:

1. Search for an existing governed document with `knowledge_search`
2. Use `knowledge_write` to create or version the document
3. Preserve provenance in both the content and `source_ref`

### 3. Query

When you ask about previously accumulated knowledge:

1. Search with `knowledge_search`
2. Ground the answer in the returned quote and complete Citation v3 URI
3. Use `knowledge_get` with that URI when more context is needed
4. Preserve the URI verbatim; never shorten, reorder, or reconstruct it. Search again if it is rejected

## Page Format

```markdown
# Page Title

> Source: <source URL or brief description>

Body content. Link between pages using relative paths:
[Related Page](../category/related-page.md)

## Key Points

- ...

## Related Pages

- [Page A](../category/page-a.md) — why it's related
```

<Note>
- `> Source:` records where this knowledge came from. Always include it when there is a clear source
- Cross-references are important: when creating or updating a page, remember to add back-links in the related pages too
- **Only link to pages that already exist.** If a concept deserves its own page, create it first, then add the link
</Note>

## Generated Index

`knowledge/index.md` is a generated compatibility projection. Its current display format is a flat list grouped by category:

```markdown
# Knowledge Index

## Category A
- [Page Title](category-a/page-slug.md) — one-line summary

## Category B
- [Page Title](category-b/page-slug.md) — one-line summary
```

Do not edit this file directly. Category names and organisation are derived from governed write operations.

## Generated Log

`knowledge/log.md` is also generated from lifecycle records:

```markdown
## [YYYY-MM-DD] ingest | Page Title
## [YYYY-MM-DD] synthesize | Page Title
```

## Writing Guidelines

- **Filenames**: lowercase with hyphens, e.g. `machine-learning.md`
- **One topic per page** — link related content across pages
- **Update, don't duplicate** — if a page already exists, update it rather than creating a new one
- **Never edit projections directly** — use `knowledge_write`, `knowledge_rollback`, or `knowledge_revoke`
- **Distill, don't copy** — capture the key points, not the entire source
- **Use complete Citation v3 URIs for grounded answers** and preserve every parameter verbatim
- **Treat `source_ref` as a source declaration**; its hash proves immutability, not external authenticity
