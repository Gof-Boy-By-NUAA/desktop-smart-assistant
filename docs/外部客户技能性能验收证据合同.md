# 外部客户技能与性能验收证据合同

## 当前状态

当前没有目标客户提供的受签名验收包、执行报告或信任根。因此：

```text
TARGET_CUSTOMER_ACCEPTANCE=NO
CUSTOMER_ATTESTATION=ABSENT
CUSTOMER_TEST_EXECUTION=NOT_RUN
SKILLS_GOLD_DATASET_VALID=NO
SKILLS_PRODUCTION_GATE_ELIGIBLE=NO
```

## Release-pair protocol v2 (2026-08-03)

Customer-package schema 2 must contain releases.baseline and
releases.candidate. Each release declares a release id, protected Git commit,
source fingerprint, artifact SHA-256, SBOM SHA-256, pinned SmartAssistant release
signing-key id, and Ed25519 signature. Baseline and candidate must differ in
all five identity/artifact fields.

The package declares hashes for agent runtime, container image, OS image,
machine profile, network policy, and provider model revision. Their canonical
JSON hash is the only valid execution_environment_sha256; each executor
receipt, event, and external evidence object binds the same value.

An executor receipt signs both requested and observed release-identity hashes.
Runner and independent verifier require both to equal the release assigned to
that arm. Packages require at least 30 paired samples and a
data.minimum_paired_samples gate.

Trust-root schema 2 separates customer_acceptance and smart_assistant_release keys.
A public key cannot appear in both purposes. External evidence commit, source
fingerprint, and artifact must exactly match the candidate release, never the
baseline.

本合同只定义未来可验证的输入边界；测试夹具、临时密钥、本地报告和同一
PR 修改后的脚本均不能把这些字段改为 `YES`。

## 必须提供的外部输入

受保护的外部验收 runner 必须设置以下环境变量。全部文件/目录都必须位于
release checkout 之外，且不能是符号链接或 Windows 重解析点：

```text
SMART_ASSISTANT_CUSTOMER_ACCEPTANCE_EVIDENCE_PATH
SMART_ASSISTANT_CUSTOMER_ACCEPTANCE_TRUST_ROOT_PATH
SMART_ASSISTANT_CUSTOMER_ACCEPTANCE_TRUST_ROOT_SHA256
SMART_ASSISTANT_CUSTOMER_ACCEPTANCE_PACKAGE_ROOT
SMART_ASSISTANT_CUSTOMER_ACCEPTANCE_REPORT_PATH
```

信任根 SHA-256 必须经独立渠道固定。信任根的 `kind` 必须为
`smart-assistant-customer-acceptance-trust-root`，并且只包含预登记的客户
Ed25519 公钥。

## 客户签名证据

客户签名的 `smart-assistant-customer-acceptance-evidence` 必须绑定：

- 当前受审 Git commit 和完整 release source fingerprint；
- 已签名制品 SHA-256 与执行环境 SHA-256；
- 外部客户包 `manifest.json` SHA-256；
- 完整外部客户报告 SHA-256；
- 客户、验收、执行标识和可解析的执行时间；
- 预登记客户信任根中的签名 key id 与 Ed25519 签名。

验证器在签名校验后重新加载客户包，并独立重算逐事件签名、Oracle、基线/
候选配对、指标、门禁和报告 `passed`。包、报告、签名、当前源码、当前
commit 中任一项不匹配均为 `INVALID`；缺任何输入均为 `ABSENT` 或
`INCOMPLETE_EXTERNAL_INPUT`。

## 性能与资源门禁

每个外部执行器回执必须经执行器私钥签名并包含：

- 正有限的 `latency_ms`；
- 正有限的 `cpu_time_ms`；
- 正整数 `peak_rss_bytes`；
- 输入/输出 token 数、请求回执、环境快照和执行器制品 SHA-256。

客户包必须设置并且验证器强制以下约束：

- `maximum_latency_ratio` 在 `(0, 1]`：候选 P95 延迟不得劣于基线；
- `minimum_throughput_ratio` 严格大于 `1`：候选串行等价吞吐必须超越基线；
- `maximum_cpu_time_ratio` 与 `maximum_peak_rss_ratio` 都在 `(0, 1]`：
  候选 CPU 消耗和 P95 峰值 RSS 不得劣于基线；
- 成功率、Bootstrap 下界、关键场景、回归数与 token 预算仍必须通过。

“串行等价吞吐”定义为相同数量请求除以两臂签名延迟总和。它是受控配对
服务率，不得伪称为未经单独压测的端到端并发吞吐。

当前两臂仅隔离单技能注入，使用的是同一受控验收环境。它是模块消融基线，
不是历史 SmartAssistant release 基线。最终项目验收还必须增加由目标客户固定的
原始 SmartAssistant baseline 与 candidate 的 Git commit、签名制品 digest、SBOM、
同环境回执及独立配对报告；在该协议存在并通过前，不得声明全项目已与
SmartAssistant baseline 持平或超越。

## 发布绑定

`release_manifest` 不再信任 checkout 内 `customer-skill-acceptance.json`
的 `passed` 字段。只有上述外部证据经过验证且 checkout 干净、所有源码被
当前 Git commit 跟踪后，客户和 Skills 金标门禁才可解除。远程受保护 CI、
独立验证者、签名制品、FDE 旅程、安装器、迁移、长稳和告警门禁仍须分别
满足；客户技能性能证据不能替代它们。
